[screenshot]

## Design docs

Openings orient in one or two sentences, then scope:

> This doc explores how we can build a more consistent, modular pattern for retrieving, managing, and persisting data in memory with an external storage interface.

> This lays out Andrew's rough vision of what our architecture and code should look like in v2. This doc may evolve later to include other aspects. Currently it focuses on which concepts will include or skip from DDD.

> This doc does not have many practical ramifications for right now and was written to provide the foundation for future architecture exploration.

Opinion in the first person, then a decision:

> Repositories in DDD meant to provide a layer of indirection and separation between the two, separating persistence logic from your business logic. However, I've lived with Active Record in Rails quite happily for many years, and don't totally buy that it's absolutely essential.

> The strict separation of layers, e.g. Infrastructure | Application | Domain, feels like what I call "highfalutin architecture" that doesn't afford us much benefit. It comes with significant weight in terms of cognitive load and boilerplate.

> This is incorrect according to Clean Architecture, and my take is that it's fine. We want to make reasonable tradeoffs that balance speed with flexibility to change design later.

> All I'm going to say is this: We don't benefit right now by passing around interfaces everywhere instead of concrete classes, and most of our objects are not that complicated, so let's not make a factory for every entity.

> But it turns out building an event-driven architecture correctly is quite hard, and we don't need it to be successful and not be overwhelmed by complexity. This is fine enough for now:

Numbers do the arguing:

> This example took 5 seconds to find. You can open any file at random in the codebase and probably find a severe lack of encapsulation.

> Core server logic stored in 8000+ line `Room.ts` file. Unable to modularize logic or write unit tests. Adding new server events requires changes in 10+ places.

Plain cause and effect:

> Without encapsulation, all consumers of a domain model intimately know how it is designed, which then makes code resistant to refactoring down the line. If we wanted to change the structure of `billingAddress` for instance, we have to grep across our entire codebase to find its many usages in leaves of our app.

> One of these updates will "win" and clobber the changes of the other update. It would be ideal to only send an `UPDATE` query for the values that were changed.

> Prisma prevents running further migrations because at this point it's unclear what is the actual schema of the DB. E.g. if the migration failed halfway through, maybe some of the statements (e.g. `ADD COLUMN ...`) completed, where others did not. Prisma can't safely proceed without knowing the state of the world. It needs to understand the state of the world, and so do you.

Bold lead-in bullets for a list of points:

> - **Batching requests.** If we fire off 5 requests in parallel, they'll get bundled into a single HTTPS request. This could lower overall load on the API server + DB, because each request requires authentication and processing that is effectively unnecessary overhead.
> - **Stop worrying about REST design.** Rather than worry about proper REST design ("should it be `/spaces?paying=true` or `/spaces/paying` or ...?"), we focus on what an intuitive structuring of an API might look like: `spaces.getAllPaid`. Arguably what we all do isn't REST anyway, so perhaps this isn't a hill worth dying on.

Dry humor from understatement, never a set-up joke:

> Models are Just TS Classes™.

> 3\. Profit. Now this repo is placed instead of the automagical one.

> This is so wildly impressive that we can do this without any other piping, I will indulge with a GIF here.

> The best way to ensure your model works and is wired properly is by writing a test. (Andrew's favorite phrase).

> Hubris led me to believe I could Do Better than Git Flow.

> "Try harder" is not a prevention measure.

Callouts and TL;DRs:

> 💡 TL;DR: Always ask if you can put state on a model/value object, rather than storing flatly as global state or creating a new repo for it.

> ⚠️ Do not call store.load("SomeModel", ...) from anywhere other than that model's repo. Otherwise it's classic bad encapsulation.

Conclusions are numbered takeaways, not a recap essay:

> 1. We place domain models (entities + value objects) at the center of our architecture
> 2. We express models as classes and lean on OOP design thinking
> 3. We created shared base classes that define logic used by both client and server
